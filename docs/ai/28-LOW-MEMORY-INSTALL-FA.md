# راهنمای نصب و بازگشت v10.10.3 — Kernel v1.6

وضعیت تحویل: **LOCAL-VALIDATED**. این بسته برای نسخهٔ v10.10.2 که طبق لاگ شما نصب شده ساخته شده است. پایان نصب، موفقیت مدل و پذیرش پاسخ در ERP سه نتیجه جدا دارند.

## نصب

۱. ZIP را Extract کن و وارد پوشه‌ای شو که `install.ps1` داخل آن است.

۲. Docker Desktop باید آماده و کانتینر Worker نسخه قبلی موجود باشد. اجرای نصاب به Python، Node یا PHP نصب‌شده روی ویندوز نیاز ندارد؛ از Python تصویر Worker استفاده می‌کند. در زمان نصب کار جدیدی به همین Worker نسپار.

۳. در PowerShell همان پوشه اجرا کن:

```powershell
powershell -ExecutionPolicy Bypass -File ".\install.ps1"
```

مسیرهای پیش‌فرض: پروژه `C:\Projects\excel-dev` و نسخه پشتیبان `C:\Projects\excel-dev-patch-backups`. اگر پروژه جای دیگری است:

```powershell
powershell -ExecutionPolicy Bypass -File ".\install.ps1" -Repo "D:\Projects\excel-dev" -BackupRoot "D:\Projects\excel-dev-patch-backups"
```

این به‌روزرسانی مستقیماً روی v10.10.2 نصب می‌شود؛ آن نسخه را دوباره نصب یا rollback نکن. فقط همین بسته را اجرا کن؛ لازم نیست بسته‌های قدیمی را دوباره نصب کنی. کپی دستی `payload` مسیر نصب استاندارد نیست، چون بررسی سازگاری، بکاپ و بازگشت را اجرا نمی‌کند.

## کارهایی که نصاب انجام می‌دهد

1. کنترل SHA-256 بسته و محتوای پایه؛ اختلاف صرفاً CRLF/LF پذیرفته می‌شود. تغییر ناشناخته در فایل لازم، پیش از نصب متوقف می‌شود. نسخه پایه، محتوای دقیق بستهٔ تحویلی v10.10.2 است؛ صرفاً برابر بودن نام نسخه کافی نیست.
2. ساخت کاندید در پوشه‌ای خارج از پروژه، بدون کپی تنظیمات محرمانه، داده‌های Worker یا Git.
3. ساخت تصویر Docker کاندید و اجرای کل تست‌های Python و بررسی import از تصویر ساخته‌شده؛ Worker قبلی در این مرحله فعال می‌ماند.
4. توقف Worker، ذخیره بایت دقیق فایل‌های تغییرکرده و وضعیت وجود/عدم‌وجود route، سپس نصب فقط فایل‌های manifest. فایل جدید در بازگشت حذف می‌شود و فایل قدیمی دقیقاً برمی‌گردد.
5. اعمال محدودیت هم‌زمانی Ollama با تصویر از قبل نصب‌شده، تشخیص ظرفیت و آزمون سه سناریوی واقعی با قرارداد تولید؛ مدل جدید دانلود نمی‌شود.
6. راه‌اندازی تصویر تست‌شده و بررسی نسخه، import، وضعیت اجرا و خطای آغاز کار.
7. ثبت گزارش نهایی و نگه‌داشتن تصویر قبلی برای بازگشت. Git commit/push و استقرار وب در این نصب انجام نمی‌شوند.

`engine/config.json`، توکن‌ها، مدل‌های دانلودشده، اسناد و دیتابیس عملیاتی دست‌نخورده می‌مانند. route انتخاب مدل در `engine/data/agent_kernel_model_route.json` به‌روز می‌شود و نسخه قبلی آن در بکاپ حفظ می‌شود. زمان پایان مکث موقت endpoint هم در فایل cooldown زیر پوشه data ثبت می‌شود؛ این فایل دادهٔ مدل/ERP ندارد و پس از حداکثر ۱۲۰ ثانیه بی‌اثر است. این بسته تغییر PHP/وب یا migration ندارد؛ برای استفاده از اصلاحات موتور، deploy جدید cPanel لازم نیست.

## ارزیابی مدل در این نسخه

درخواست اول هر مدل حداکثر ۶۰ ثانیه و دو سناریوی بعدی هرکدام ۳۰ ثانیه فرصت دارند؛ سقف پیش‌فرض کل ارزیابی ۲۴۰ ثانیه است. محدودیت‌های کوچک‌تر موجود در تنظیمات همچنان اعمال می‌شوند. این انتظار فقط برای ارزیابی نصاب است. پس از timeout، همان سرویس ۳۰ ثانیه مکث می‌گیرد؛ نصاب در صورت داشتن بودجه زمانی، پایان مکث را منتظر می‌ماند و سپس مدل بعدی را بررسی می‌کند. اگر زمان کافی نباشد، مدل بعدی روی آن با `SKIPPED / endpoint_cooling` ثبت می‌شود. این وضعیت، شکست معنایی آن مدل نیست. این نصب مدل جدید دانلود نمی‌کند و حافظه را با حذف حفاظ‌ها آزاد فرض نمی‌کند.

زمان اولین تکه، اولین متن، شمار نویسه‌های thinking و content، نوع استثنا، وضعیت HTTP و نتیجه هر سناریو در خروجی چاپ و در `model-qualification.json` ذخیره می‌شوند. `runtime-diagnostics.json` و `runtime-diagnostics-after.json` وضعیت قبل و بعد از ارزیابی را نشان می‌دهند. فیلدهای Ollama دارای پسوند duration بر حسب نانوثانیه هستند؛ `elapsed_seconds` بر حسب ثانیه است.

در پاسخ محصول، سقف پیش‌فرض Kernel اکنون ۷۵ ثانیه و هر تلاش تولید حداکثر ۶۰ ثانیه است. این تغییر فرصت بیشتری به بارگذاری می‌دهد؛ تضمین نمی‌کند روی دستگاه فعلی پاسخ کامل شود. اگر `kernel_budget_seconds` یا `local_runtime.max_call_seconds` را قبلاً کوچک‌تر تنظیم کرده‌ای، نصاب آن‌ها را بازنویسی نمی‌کند.

## معنی نتیجه‌ها

| خروجی | معنی |
| --- | --- |
| `FILE_INSTALL=PASS` | فایل‌ها، تصویر و تست‌های نصب بررسی شده‌اند. |
| `MODEL=PASS_3_SCENARIOS` | یک مدل در همین موتور سه آزمون انتخاب یافته را گذرانده است؛ این آزمون، ارزیابی جامع استدلال نیست. |
| `MODEL=DEGRADED` | هیچ مدل پیکربندی‌شده واجد قرارداد نشده؛ پاسخ خوانش‌های پشتیبانی‌شده از مسیر قاعده‌محور می‌آید. مشکل پاسخ مدل هنوز تأیید رفع نشده است. |
| `ERP_LIVE=PENDING` | کیفیت پاسخ با داده واقعی و UI هنوز باید بررسی شود. |

حالت DEGRADED به‌وضوح گزارش می‌شود و موفقیت مدل نام نمی‌گیرد. اگر الزام داری با قبول‌نشدن مدل کل نصب برگردد، از ابتدا گزینه `-RequireModel` را به فرمان نصب اضافه کن. خطای ساخت، تست، نسخه، import یا نصب در هر دو حالت موجب تلاش برای بازگشت خودکار می‌شود.

اگر Docker یا سیستم هنگام نصب قطع شود، بازگشت خودکار ممکن است کامل نشود. مسیر بکاپ چاپ‌شده و فرمان زیر برای بازیابی بعد از آماده‌شدن Docker هستند. بسته هیچ حجم Docker را حذف نمی‌کند.

## بازگشت

از داخل پوشه بسته یا با اسکریپت کپی‌شده در پوشه بکاپ:

```powershell
powershell -ExecutionPolicy Bypass -File ".\rollback.ps1" -BackupDir "C:\Projects\excel-dev-patch-backups\v10.10.3-before-TIMESTAMP"
```

`TIMESTAMP` را با نام واقعی چاپ‌شده توسط نصاب جایگزین کن. اگر مسیر پروژه متفاوت است، همان `-Repo` نصب را هم بده. تصویر قبلی Worker باید هنوز موجود باشد؛ تا پایان تأیید نسخه، آن را با image prune پاک نکن. بازگشت، فایل تغییریافته بعد از نصب را بی‌اطلاع بازنویسی نمی‌کند و در تعارض متوقف می‌شود.

## بررسی در نرم‌افزار

بعد از نصب، سه خوانش زیر را اجرا کن؛ برای موردهای دوم و سوم موجودیت واقعی را با @ انتخاب کن:

1. «تأمین‌کننده‌های ما را از نظر عملکرد خرید بررسی و مقایسه کن. بگو کدام‌ها بهتر و کدام‌ها پرریسک‌تر هستند و دلیل هر نتیجه را از داده‌های ERP بگو.»
2. «ریسک این پرونده بازرگانی را بررسی کن و مهم‌ترین اقدام بعدی را بگو.» همراه @پرونده مشخص.
3. «تأخیر این محموله چه اثری روی تعهدهای فروش دارد؟» همراه @محموله یا @پرونده مرتبطِ پشتیبانی‌شده.

معیار پذیرش: نام و وضعیت هر تأمین‌کننده در پوشش پاسخ دیده شود؛ پرونده پرریسک گم نشود؛ صفر بودن دریافت با بدقولی یکی نشود؛ پرونده انتخابی با پرونده دیگری عوض نشود؛ اعداد با ERP همان شرکت تطبیق داشته باشند؛ اثر احتمالی حمل با رابطه علّی اثبات‌شده اشتباه نشود. بازه پیش‌فرض مقایسه شش ماه و پوشش حداکثر پنج تأمین‌کننده است؛ بازه‌های پشتیبانی‌شده یک تا دوازده ماه گذشته‌اند.

برای ادامه بررسی، خروجی نصب یا این فایل‌های پوشه بکاپ را بفرست: `install-result.json`، `model-qualification.json` و `runtime-diagnostics.json` و `runtime-diagnostics-after.json`، به‌همراه متن جواب سه خوانش. برای ادامه، متن کامل خروجی نصب به‌تنهایی نیز قابل استفاده است؛ خطاهای جدید با جزئیات محدود چاپ می‌شوند. فایل تنظیمات یا توکن لازم نیست.

## دستگاه دوم و RAG

دستگاه دوم اختیاری است و در نصب فعال نمی‌شود. تنظیم endpoint و محدودیت‌های آن در سند ۲۷ آمده است؛ ماشین دوم RAM مدل را با ماشین اول جمع نمی‌کند. RAG نیز پیش‌فرض غیرفعال می‌ماند. آماده‌سازی ingestion با دسترسی هر سند، حذف‌ها و ارزیابی بازیابی، مرحله بعدی مستقل است.
